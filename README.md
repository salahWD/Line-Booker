# دوري — Live lines & paid appointments

An Arabic-first (RTL), mobile-first web app built around **two features**:

1. **Live lines ("take a number").** A customer takes a number in a branch line (for example a hospital clinic). They see how many people are ahead, the pace of the line and an estimated wait and call time, so they can leave and come back. Shortly before their turn their phone gets a **push notification** (Firebase), with **SMS as the fallback**, then a "your turn" alert. The tracker page rings and vibrates when they are called.
2. **Paid date-and-time appointments.** Owners publish free time slots. The customer picks one and the slot is **held** while they pay the branch's fee through the **platform's Whish Money link**. The **platform admin** checks the Whish account and confirms (or rejects) the payment manually. Only then is the appointment confirmed.

Everything else (operator console, waiting-room display, notes, reviews, reports, admin tools) supports these two flows.

## Quick start (development)

Requirements: **Node.js 20+** and **MariaDB 10.6+ or MySQL 8** (for example from XAMPP, Laragon, the MariaDB installer or `docker run -e MARIADB_ROOT_PASSWORD=root -p 3306:3306 mariadb:11.8`).

```bash
npm install
cp .env.example .env        # set DATABASE_URL, SESSION_SECRET and OTP_SECRET

# Create an empty UTF-8 database once (name must match DATABASE_URL):
#   CREATE DATABASE booking CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;

npm run db:reset            # empties the DB, applies migrations, loads Arabic demo data
npm run css:build           # builds src/public/css/app.css (Tailwind)
npm run dev                 # web server + jobs + CSS watcher → http://localhost:3000
```

> The demo data is time-sensitive: it creates *today's* live queues and a hold that expires in 25 minutes. Run `npm run db:reset` again (with the app stopped) whenever you want a fresh demo.

Deploying to Hostinger (or any Node host with MySQL): see **[Deploying to Hostinger](#deploying-to-hostinger)** below.

## Architecture

MVC with a **service layer**. Controllers are thin, all business rules live in services, and all SQL lives in models.

```
src/
  server.js / worker.js     entry points (web + jobs, or jobs only)
  app.js                    express wiring: helmet CSP, static, sessions, CSRF, routes, errors
  config/                   env (zod-validated), db (pool + drizzle + transaction helper), constants
  routes/                   URL → controller, plus role checks per router
  controllers/              parse input → call a service → render HTML or return JSON
  services/                 business rules (see below)
  models/                   persistence only; schema/ holds the Drizzle table definitions
  middleware/               auth, CSRF, validation, rate limits, uploads, id params, errors, view locals
  validators/               zod schemas for every form / JSON body
  jobs/                     job runner: sweeps (notifications, holds, alerts, reminders), day close, cleanup
  integrations/sms|push/    provider adapters (+ clearly labelled development mocks)
  locales/ar.js             every UI string (add another file to support another language)
  views/                    layouts / partials / pages per area
  public/                   css (Tailwind input + build), js (Alpine components), images, manifest
database/migrations/        generated SQL migrations (commit them)
database/seeds/seed.js      Arabic demo data
scripts/                    migrate, reset, create-admin, check-critical-flows
```

**Request flow example** ("call next"): `routes/operator.routes.js` → `controllers/operator.controller.js#callNext` → `services/line.service.js#callNext`. In one transaction, the service locks the line, picks the next ticket with `queueOrder.service`, updates the ticket only if it is still `waiting`, and queues the "your turn" notification. After commit, the notification is sent and every open screen gets an SSE event and re-fetches its own state.

### Key services

| Service | Responsibility |
|---|---|
| `access.service` | Business/branch isolation: admin = all, owner = own business, operator = assigned branches. Anything else is answered with **404**. |
| `line.service` | Take a number, check-in, call/recall/complete/skip/restore/cancel, pause/open, and the read models for the tracker, operator console and display. |
| `queueOrder.service` | The ordering policy (pure function, easy to test). |
| `estimate.service` | Waiting-time estimate and range. |
| `alert.service` | "Approaching" and "your turn" alerts. |
| `availability.service` | Slot generator, the owner's calendar, and bookable dates/times. |
| `appointment.service` | Hold, expiry, cancel, reschedule, no-show, reminders. |
| `payment.service` | Whish panel + QR, transfer submission, admin confirm/reject. |
| `notification.service` | Outbox, push → SMS fallback, delivery tracking. |
| `note.service`, `review.service`, `report.service`, `audit.service` | Notes with visibility rules, reviews, reports, audit log. |

## Feature 1 — live lines

- **Lines.** A branch has one or more named lines (e.g. "عيادة الأطفال"). Each line has its own numbering (`A-012`), average minutes per customer, number of counters, ordering policy and display.
- **Taking a number** requires a verified phone, so the customer can be alerted and duplicates can be prevented.
  - From the branch page this works only if the line allows remote joining and the branch is open.
  - The QR poster link `/join/<line token>` (shown in the branch settings) always works.
  - Operators can add walk-ins without a phone.
  - If the customer already has an active ticket in that line, they get the same ticket back.
  - If they have an appointment today on that line, taking a number becomes a **check-in**. A walk-in ticket taken earlier is upgraded instead of creating a second one. Unique indexes on an "active" generated column guarantee this at database level too.
- **Ordering policy** (per line, explained to customers on the page):
  - `fifo`: everyone by arrival time.
  - `booked_first`: on-time appointment holders by appointment time, then walk-ins.
  - `interleave` (default): N appointment holders, then 1 walk-in (N = `interleave_ratio`).
  - Appointment holders arriving later than slot + `late_grace_minutes` are treated as walk-ins.
- **Ticket states:** `waiting → called → completed`. Recall keeps the ticket called and alerts again. Tickets can also go `called/waiting → skipped → waiting` (restore) or `→ cancelled`. Leftovers become `expired` at day close, and a linked appointment becomes completed / cancelled / no-show accordingly.
- **Concurrency.** Every queue action runs in a READ COMMITTED transaction that first locks the line's row in `line_locks` (held until commit) and uses conditional updates (`… WHERE status IN (…)`). Two operators pressing "call next" together always get different tickets. The second operator to act on the same ticket gets a clear "already handled" message.
- **Estimate** (`estimate.service`):
  - The pace ("one number every X minutes") comes from, in order of preference:
    - today's calls in the last 2 hours, with paused time excluded (at least 5 gaps);
    - the same weekday ±1 h over the last 4 weeks (at least 8 gaps);
    - the owner's average minutes ÷ number of counters.
  - People ahead are reduced by today's skip rate.
  - wait ≈ ahead × pace + pace/2.
  - It is shown as a range (wider when the data is weaker) together with the expected call times and an "updated at" time.
  - The first estimate is stored on each ticket and the real wait is recorded on the first call. Reports compare the two (% within range, mean error).
- **Alerts** (`alert.service`), checked after every queue change and by the job sweep every 15 s:
  - **Approaching** is sent once, when the estimate drops to the customer's chosen lead time (10–60 min) or only `alert_ahead_threshold` people are left.
  - **Your turn** is sent on call and again on recall.
  - Delivery is FCM web push to all of the customer's devices (high urgency, requireInteraction, vibration). It falls back to SMS when there is no device or the push fails.
- **Live screens.** The tracker, operator console, branch page and display use SSE. They reconnect with backoff, re-fetch after every reconnection, show a "disconnected" banner, and poll every 30 s as a safety net.

## Feature 2 — paid appointments

```
pick slot ──hold()──▶ held + unpaid ──(hold minutes pass)──▶ expired (slot released)
                         │ customer: "قمت بالتحويل" (+ ref, optional proof)
                         ▼
                      held + awaiting_verification   (slot stays reserved)
                         │ platform admin confirms ─▶ confirmed + payment confirmed (who/when recorded)
                         │ platform admin rejects  ─▶ cancelled + payment rejected (slot released)
confirmed ─check-in on the day─▶ checked_in (ticket in the line) ─▶ completed ─▶ 1 review
          ─never came─▶ no_show        held/confirmed ─cancel (before cutoff)─▶ cancelled
```

- **No overbooking.** `UPDATE appointment_slots SET reserved_count = reserved_count + 1 WHERE id = ? AND is_open AND reserved_count < capacity` is a single atomic statement (0 rows matched = full), and a CHECK constraint backs it up. Every release decrements the count in the same transaction as the status change.
- **Fees** are set per branch by the owner (amount, USD/LBP, deposit or full). A snapshot is saved on each appointment. A fee of 0 confirms instantly.
- **Payment page.** It shows the branch, reference, exact amount and currency, deposit or full, the steps, and the **platform's Whish link exactly as saved**, as a button and a QR code. The URL is never modified and the amount is never assumed to be pre-filled.
  - Clicking the link or submitting proof **never** marks anything as paid.
  - Proof files are checked by their bytes (jpeg/png/webp/pdf, ≤ 5 MB), stored outside `public/` with random names, and visible only to the admin and the uploader.
- **No wallet, balances, automatic transfers or refunds.** Refunds and the payouts to businesses are done manually. Admin → "تسوية المؤسسات" lists the fees the platform confirmed, per business and branch, with CSV export.

## Notes, reviews, reports

- **Notes** have three kinds:
  - `customer`: written by the customer.
  - `internal`: staff only. Never returned by any customer-facing query.
  - `shared`: written by staff and visible to the customer.

  Visibility is enforced in `note.service` / `appointment.service.customerView`.
- **Reviews.** One per completed appointment (unique constraint), with an owner reply. They are shown on the branch page.
- **Reports** (owner): appointments, attendance, cancellations/expiries, ticket volume (walk-in vs. appointment), real waiting time (average and p90), estimate accuracy, expected fees and admin-confirmed fees. Filters are date, branch and line, with Chart.js charts and CSV exports. The CSVs have a UTF-8 BOM so Excel shows Arabic correctly, and formula injection is neutralised.

## Notifications

- **Outbox pattern.** Notification rows are written inside the business transaction and sent right after commit. A failed attempt is retried by the job sweep with backoff (15 s, 30 s, 1 min, 2 min; 5 tries). Statuses are `queued → sending → sent → delivered/failed`. A row stuck in `sending` (e.g. the app restarted mid-send) is retried after 10 minutes.
- **OTP.** 6 digits, HMAC-hashed, 5-minute validity, 5 attempts, 60 s resend cooldown, 5 per hour per phone, plus a per-IP rate limit. The SMS text is redacted in the log, and the plaintext is wiped once sent.
- **SMS providers** (`SMS_PROVIDER`):
  - `mock` (**development only — nothing is sent**; see the console and `/dev/notifications`).
  - `twilio` (REST API). Delivery callbacks go to `POST /webhooks/sms/twilio?secret=SMS_WEBHOOK_SECRET`.
  - To add a provider, create `integrations/sms/<name>.provider.js` with `send({ to, body })` and register it in `integrations/sms/index.js`.
- **Push (Firebase).**
  1. Create a Firebase project.
  2. Add a web app.
  3. Generate a Web Push key pair (Cloud Messaging).
  4. Create a service-account key.
  5. Fill in the `FIREBASE_*` variables.

  Without them the push **mock** is used. In mock mode "enable notifications" registers a fake device, so the push → SMS fallback logic still runs. On iPhone, web push only works after "Add to Home Screen" (iOS 16.4+); the app ships a manifest and shows this hint.

## Security

- **Server-side checks.** Every input is validated with Zod. Every staff query is scoped through `access.service`, and `business_id` always comes from the session. Numeric route ids are checked, so anything else gets a 404.
- **Sessions** are stored in MySQL: httpOnly, SameSite=Lax, secure in production, regenerated at login. Staff sessions last 12 h, customer sessions 30 days.
- **CSRF** uses a synchronizer token (hidden `_csrf` field or the `X-CSRF-Token` header). Multipart uploads are verified right after parsing.
- **Rate limits** apply to login, OTP, booking, joining, uploads and the JSON APIs. They are kept in memory; use a shared store if you run several instances.
- **Strict CSP** via helmet: no inline scripts and no `eval` (that is why the Alpine **CSP build** is used); page data is passed in escaped `data-*` attributes.
- **Passwords** are hashed with bcrypt; there are no stack traces in production responses.
- **Audit log** covers platform settings, businesses, branches, lines, slot bulk actions, operators, payment decisions, display tokens, staff cancellations and review replies.

## Critical-workflow checks

`npm run check` (`scripts/check-critical-flows.js`) creates its own isolated businesses, users and lines, runs **34 checks** through the same services the routes use, and deletes everything afterwards:

- **Branch isolation:** another business's owner and unassigned operators get 404 on branches, lines, tickets, appointments and notes.
- **Simultaneous bookings:** 20 parallel bookings on a capacity-1 slot → exactly 1 succeeds; on capacity 3 → exactly 3. Expired holds and rejected payments release the slot.
- **Queue transitions:**
  - The policies order tickets correctly, including on a real line.
  - Two parallel "call next" presses get different tickets.
  - Invalid moves are rejected with 409.
  - Check-in never creates a duplicate ticket.
  - A staff cancellation of a checked-in appointment also removes its ticket.
  - The "approaching" alert is sent once even with parallel checks.
- **Note privacy:** customers never receive internal notes and cannot write internal or shared ones.
- **Payment permissions:**
  - Submitting proof only sets "awaiting verification".
  - Customer, owner and operator cannot confirm.
  - The admin can confirm once, and who and when are recorded and audited.

## Assumptions & limitations

- **Region:** Lebanon. The default timezone is `Asia/Beirut` (configurable per branch), currencies are USD and LBP, phones are normalised to E.164 (default country LB), and Western digits are used.
- **Language:** the UI is Arabic only. All strings are in `src/locales/ar.js`.
- **Appointments** are always date + time; date-only bookings were dropped in favour of the take-a-number line.
- **Ownership:** one business per owner. Operators belong to one business and are assigned to branches; they are never chosen by customers.
- **Whish Money** is a manual link by design: there is no API integration. The seed uses a **placeholder link**, so set the real one in Admin → Settings.
- **Mocked or untested:** SMS is mocked in development. Twilio is implemented from its REST docs but **not tested against a live account**. Push runs as a mock until the Firebase credentials are set.
- **Phone "ringing"** means a high-priority push with vibration plus a looping alarm on the open tracker page. Placing a real phone call (e.g. a voice API) is not implemented.
- **Rate limiting** and **live-update broadcasts** are in memory, which suits one Node process (how shared hosting runs it). With several processes, screens still update through their 30 s polling fallback.
- **No automated test suite**, as requested; `npm run check` covers the critical flows.

## Deploying to Hostinger

Hostinger's **Business / Unlimited** web hosting (and Cloud plans) run Node.js web apps with a MariaDB database. Premium does not run Node.js.

**How Hostinger runs the app** (seen on the server):
- hPanel clones the GitHub branch, runs `npm install` and `npm run build`, and keeps each build in `~/domains/DOMAIN/hbuilds/versions/<id>/nodejs`. `hbuilds/current` points at the live one.
- **Pushing to the connected branch redeploys automatically.**
- LiteSpeed runs the entry file through Passenger. The app must call `listen()` within about 3 seconds: `src/server.js` listens first and answers 503 until migrations and jobs are ready (a first migration takes several seconds).
- Console output goes to `hbuilds/current/nodejs/console.log`. `touch hbuilds/current/nodejs/tmp/restart.txt` restarts the app.
- Each build gets a fresh folder, so anything written inside the app folder is lost on the next deploy. Uploads and settings live outside it.

### One-time setup
1. **Database.** hPanel → Databases → Management: create a database and user (host `localhost` for the app).
2. **Private settings file.** Settings live in `~/dawri/.env` (chmod 600, outside the app folder), with payment proofs in `~/dawri/uploads`. The app loads the file through `ENV_FILE`, so it survives redeploys and can be edited over SSH. It needs:
   - `NODE_ENV=production`, `APP_URL=https://your-domain`, `TRUST_PROXY=1`;
   - `DATABASE_URL=mysql://USER:PASSWORD@localhost:3306/DATABASE` (URL-encode special characters);
   - `RUN_MIGRATIONS=true`, `RUN_JOBS=true`, `DB_POOL_SIZE=5`;
   - random `SESSION_SECRET`, `OTP_SECRET`, `CRON_SECRET`, `SMS_WEBHOOK_SECRET`;
   - `UPLOAD_DIR=/home/USER/dawri/uploads`;
   - `SMS_PROVIDER=twilio` + `TWILIO_*` (customers cannot sign in without real SMS), and optionally `FIREBASE_*`.
3. **App.** hPanel → Websites → Add website → **Node.js web app** → import from GitHub (this repository, branch `main`):
   - Framework **Express** (or Other), Node **22**, package manager npm;
   - build command `npm run build`, entry file `src/server.js`;
   - one environment variable: `ENV_FILE=/home/USER/dawri/.env`.
4. **First admin**, over SSH from the live build folder:
   ```
   cd ~/domains/DOMAIN/hbuilds/current/nodejs
   ENV_FILE=~/dawri/.env /opt/alt/alt-nodejs22/root/usr/bin/node scripts/create-admin.js --email you@example.com --password 'a-long-password'
   ```
   Then sign in at `/staff/login` and set the real Whish link in Admin → Settings.
5. **Cron job** (hPanel → Advanced → Cron Jobs; there is no `crontab` over SSH), every minute:
   `curl -s "https://your-domain/internal/tick?key=CRON_SECRET" > /dev/null`
   This keeps alerts, hold expiry and retries running even when the host pauses an idle app.
6. **Never** run `npm run db:seed` / `db:reset` on the live site: they refuse in production anyway.

### Later deploys
Push (or merge) to `main`: Hostinger rebuilds and restarts, and pending migrations run on start. Check `console.log` and `/healthz` afterwards.
